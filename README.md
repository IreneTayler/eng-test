### Аутентификация

Работал и с JWT, и с классической session-based авторизацией. JWT хорошо подходил для API и систем, где было несколько клиентов (web, mobile) или несколько сервисов, которым нужно было независимо проверять права пользователя без хранения сессий на сервере.

При этом для внутренних систем и административных панелей JWT не всегда выглядел оптимальным решением. Помимо самого access token приходилось поддерживать refresh token, механизмы logout и отзыва токенов, что добавляло дополнительную сложность. На одном из проектов со временем пришли к выводу, что обычные httpOnly cookies с хранением сессий в Redis были бы проще в реализации и дешевле в поддержке.

После этого опыта перестал воспринимать JWT как решение по умолчанию. Сейчас выбор зависит от архитектуры системы и требований проекта. Для распределённых сервисов и внешних API я бы по-прежнему выбрал JWT, а для монолитных внутренних систем часто предпочёл бы классические серверные сессии.

### Идентификация

UUID использовал в публичных API, чтобы не раскрывать последовательные идентификаторы и снизить риск enumeration-атак. Для внешних клиентов такой подход выглядит более безопасным и удобным.

Однако на проектах с большими объёмами данных использование UUID создавало определённые проблемы. В частности, в PostgreSQL становились заметны дополнительные затраты на индексацию и вставку записей по сравнению с обычными bigint-идентификаторами. На одном из проектов часть таблиц в итоге перевели обратно на bigint в качестве первичного ключа, а UUID оставили только для внешнего API.

С тех пор стараюсь выбирать тип идентификатора исходя из требований конкретной системы, а не использовать UUID как универсальный стандарт для всех таблиц.

### Организация кода

В NestJS мне нравится то, что он помогает поддерживать понятную структуру проекта, особенно когда над системой работает несколько разработчиков. Разделение на controllers, services и другие слои делает код более предсказуемым и упрощает навигацию по проекту.

Dependency Injection хорошо себя показывал в задачах, где требовалось подменять реализации или писать тесты. Например, на одном из проектов благодаря DI удалось без серьёзных изменений бизнес-логики переключаться между различными storage-провайдерами.

Middleware и interceptors использовались для логирования, трассировки запросов и сбора технических метрик, что упрощало поддержку и диагностику проблем в production.

При этом видел и обратную сторону такого подхода. В небольших проектах NestJS иногда приводит к появлению большого количества boilerplate-кода и абстракций, которые не дают заметной практической пользы. Поэтому сейчас стараюсь соблюдать баланс между архитектурной чистотой и реальной сложностью проекта.

### Реактивность

React считаю очень удобным инструментом для сложных интерфейсов и крупных SPA-приложений. Реактивный подход хорошо работает в большинстве бизнес-задач и позволяет быстро разрабатывать пользовательские интерфейсы.

Тем не менее были ситуации, когда реактивность становилась источником дополнительных сложностей. Например, на одном dashboard-проекте с большим количеством realtime-обновлений пришлось уделять значительное внимание оптимизации ререндеров, мемоизации и структуре состояния приложения. В таких случаях часть времени уходит не на решение бизнес-задач, а на работу с особенностями самого фреймворка.

Отдельно могу отметить, что некоторые проблемы в React связаны с использованием hooks и контролем жизненного цикла компонентов. Ошибки в зависимостях useEffect или неудачная организация состояния могут приводить к лишним запросам, лишним ререндерам и трудноуловимым багам.

Несмотря на это, для большинства веб-проектов React остаётся для меня одним из самых удобных инструментов благодаря зрелой экосистеме, большому количеству готовых решений и высокой скорости разработки. Со временем я просто пришёл к пониманию, что реактивность — это мощный инструмент, но не универсальное решение для любых UI-задач.
