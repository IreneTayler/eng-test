# Аутентификация

Работал и с JWT, и с обычной session-based авторизацией. JWT хорошо подходил для API и сервисов, где было несколько клиентов (web/mobile) и не хотелось хранить сессии на сервере. Но для внутренних систем и админок он часто только добавлял сложности: refresh token, logout, revoke. В одном проекте в итоге поняли, что обычные httpOnly cookies + Redis были бы проще и дешевле в поддержке. После этого стал спокойнее относиться к JWT и не использовать его “по умолчанию”.

# Идентификация

UUID использовал в публичных API, чтобы не светить последовательные id. Это удобно и безопаснее с точки зрения enumeration. Но в больших таблицах UUID создавал проблемы с индексами и insert performance, особенно в PostgreSQL. На одном проекте часть таблиц перевели обратно на bigint, а UUID оставили только наружу для API. С тех пор стараюсь выбирать тип идентификатора под задачу, а не использовать UUID везде.

# Организация кода

С NestJS нравится то, что он помогает держать проект структурированным, особенно когда команда растет. DI и разделение на services/controllers сильно упрощали тестирование и замену реализаций, например для разных storage provider’ов. Middleware и interceptors были полезны для логирования и tracing. Но видел и обратную сторону: когда проект маленький, появляется слишком много boilerplate и абстракций ради “красивой архитектуры”. Поэтому сейчас стараюсь держать баланс между чистотой архитектуры и реальной сложностью проекта.

# Реактивность

React удобен для сложных интерфейсов и больших SPA, но иногда реактивность начинает мешать. На dashboard-проекте с постоянными realtime-обновлениями пришлось много времени тратить на оптимизацию rerender’ов и memoization. Некоторые проблемы в React вообще связаны не с бизнес-логикой, а с hooks и lifecycle. При этом для обычных интерфейсов React все равно остается самым удобным вариантом из-за экосистемы и скорости разработки. Просто со временем понял, что реактивность — это не универсальное решение для любых UI-задач.
